# 18. פרופיל בניין, התאמה אישית ומצבים מיוחדים

## 18.1 עיקרון

**כל בניין שונה, והמערכת מתאימה את עצמה לבניין.** מספר דיירים, קומות, ציוד, מערכות בטיחות, אלמנטים מיוחדים כמו חניון תת-קרקעי, ומצבים זמניים כמו שיפוץ או הצפה, כולם מוגדרים בפרופיל הבניין. הפרופיל **קובע מה המערכת מציגה ודורשת**: אישורים, תכניות תחזוקה, סעיפי ביקורת, קטגוריות תקלה והודעות.

העיקרון חל על כל מודול. כל מודול חדש חייב לבדוק איך הוא מושפע מפרופיל הבניין, ולא להניח מבנה קבוע.

## 18.2 מבנה הבניין (עץ)

```
בניין
 ├── כניסה A
 │    ├── קומה -2 (חניון תת-קרקעי)
 │    ├── קומה -1 (מחסנים, מקלט)
 │    ├── קומה 0 (לובי)
 │    ├── קומה 1 … N
 │    │    └── דירה / משרד
 │    └── גג
 └── אלמנטים חיצוניים (חצר, גינה, מתקני משחק, חניה עילית)
```

- **סוגי צמתים**: בניין, כניסה/אגף, קומה (כולל קומות שליליות), יחידה (דירה, משרד, חנות, מחסן, חניה), שטח משותף ואלמנט.
- **קטלוג אלמנטים** שאפשר להוסיף בכל שלב: חניון תת-קרקעי, מקלט או ממ"ק, חדר משאבות, חדר חשמל, חדר אשפה, גג, בריכה, חדר כושר, חדר דיירים או ישיבות, לובי, מחסנים, גינה, מתקני משחק ועוד.
- **שדות ליבה** לבניין: סוג (מגורים / משרדים / מעורב), כתובת, שנת בנייה, מספר קומות מעל הקרקע ומתחתיה, מספר יחידות, מספר דיירים (אופציונלי), שטח, גובה (חשוב לדרישות כיבוי אש בבניין רב-קומות) ותקופת בדק.
- **שדות מותאמים** לכל סוג צומת (טקסט, מספר, תאריך, רשימה, כן/לא).

## 18.3 קטלוג ציוד ומערכות

- **קטלוג הפלטפורמה** (מנוהל על ידך): מעלית, משאבות (מים, ביוב, ניקוז), גנרטור, מאגרי מים, ספרינקלרים, גלאי עשן, לוח גילוי אש, ארגזי כיבוי ומטפים, שחרור עשן, תאורת חירום, מערכת גז מרכזית, מיזוג מרכזי (VRF / צ'ילרים), יחידות מיזוג, אינטרקום, בקרת כניסה, שערים ומחסומים, מערכת סולארית, דוד מרכזי, מצלמות, טעינת רכבים ועוד.
- **סוגי ציוד של הלקוח**: הלקוח יכול **גם** להוסיף שדות לסוג קיים מהקטלוג, **וגם** להגדיר סוג ציוד חדש לגמרי עם שדות משלו.
- **שדות לכל סוג**: למעלית, למשל: יצרן, דגם, מספר תחנות, עומס, מעלית שבת, מעלית כבאים ושנת התקנה.
- **מיקום**: כל צומת בעץ, **כולל בתוך דירה או משרד**.
- **אחריות** לכל פריט ציוד:
  - רכוש משותף.
  - בעל היחידה.
  - חברת הניהול בחוזה תחזוקה. רלוונטי במשרדים, כשחברת הניהול היא גם חברת האחזקה.
  
  האחריות קובעת מי מקבל את התקלה, מי משלם, ומה נכנס לתכנית התחזוקה של חברת הניהול.

## 18.4 כללים נגזרים: הפרופיל מפעיל את המערכת

כלל = **תנאי בפרופיל ← השפעות**. הכללים מוגדרים כתבניות שאפשר לערוך, לא בקוד.

| תנאי | השפעות (ברירת מחדל) |
|------|----------------------|
| יש ספרינקלרים | אישור תקינות שנתי, תכנית תחזוקה, סעיף בביקורת בטיחות, קטגוריית תקלה (חומרה S1 לדליפה או כשל) |
| יש מעלית | תסקיר בודק מוסמך (תדירות לפי דין), חוזה שירות, קטגוריות תקלה, דוח זמינות |
| יש חניון תת-קרקעי | בדיקת מערכת אוורור ו-CO, ניקוז ומשאבות, שער חניון, תאורה, ומצב "הצפה" מוכן מראש |
| יש מקלט או ממ"ק | צ'קליסט מוכנות לחירום, אחראי, בדיקה תקופתית |
| יש גנרטור | הפעלת בדיקה חודשית, תדלוק, טיפול שנתי |
| מערכת גז מרכזית | אישור בודק גז, קטגוריית "ריח גז" בחומרה S1 |
| בניין רב-קומות | דרישות כיבוי מורחבות, לחץ בחדרי מדרגות, מעלית כבאים |
| בניין חדש (בתוך תקופת הבדק) | ליקויים ברכוש המשותף מנותבים לקבלן, התראה לפני תום הבדק |
| אין מעלית | הסתרת כל מה שקשור למעליות |
| בריכה | אישור משרד הבריאות, בדיקות מים, שעות פתיחה והזמנות |
| משרדים: מיזוג באחריות חברת הניהול | תחזוקה מונעת ליחידות בתוך המשרדים, וחיוב לפי חוזה |

**ההשפעות האפשריות**:
- אישורים נדרשים.
- תבניות תחזוקה.
- סעיפי ביקורת.
- קטגוריות תקלה וחומרה.
- קבוצות להודעות (למשל "בעלי חניה בחניון").
- מצבים מיוחדים זמינים.
- הצגה או הסתרה של מסכים.
- שדות חובה.

**ביצוע**: כשהפרופיל משתנה, המערכת מציגה מה ייווצר או ישתנה ומבקשת אישור. לדוגמה: "הוספת ספרינקלרים תיצור 3 דרישות חדשות. לאשר?". כך שום דבר לא נוצר בלי ידיעת המשתמש.

## 18.5 מצבים מיוחדים (Building States)

- **קטלוג קבוע** של מצבים, **ובנוסף מצבים שהלקוח מגדיר** עם השפעות משלו.
- **היקף**: כל הבניין, צומת (כניסה, קומה, חניון) או פריט ציוד.
- **זמנים**: התחלה וסיום מתוכננים ובפועל. המערכת מתריעה על מצב פתוח שחרג מהסיום המתוכנן.
- **מי מפעיל**: ועד או חברת ניהול. גורמים אחרים, כמו טכנאי, מבקר או חיישן, **מציעים** הפעלה, וזו נכנסת לאישור.

| מצב | השפעות ברירת מחדל |
|-----|--------------------|
| שיפוץ (רכוש משותף) | באנר לדיירים, הודעה על שעות עבודה, **חיוב מיוחד** (ראה 18.6), קישור ל-RFQ או פרויקט, חסימת שטחים |
| הצפה | תקלה S1 אוטומטית, הודעת חירום לקבוצה רלוונטית (למשל בעלי חניה), תיעוד לביטוח, קישור לתביעה |
| הפסקת חשמל / מים | הודעה לכל הדיירים, השהיית SLA לתקלות תלויות, עדכון סיום |
| מעלית מושבתת | באנר, הודעה, מעקב מול ספק המעליות, עדכון זמינות |
| חירום / מלחמה | מצב חירום (מסמך 16): הודעות בכל הערוצים, מקלט, "אני בסדר" |
| עבודות תמ"א / פינוי-בינוי | באנר, לוח זמנים, מסמכים, מגבלות גישה |
| הדברה | הודעה מראש, הנחיות לדיירים |
| מצב שהלקוח מגדיר | בחירה מתוך רשימת ההשפעות |

**רשימת ההשפעות שניתנות להגדרה**:
- באנר באפליקציה.
- הודעה לפי קבוצה, ערוץ ותדירות (מסמך 17).
- שינוי זמני של SLA.
- חסימת הזמנת מתקנים.
- פתיחת תקלה.
- יצירת חיוב מיוחד.
- קישור ל-RFQ.
- תיעוד לביטוח.
- רישום בציר הזמן.

## 18.6 חיבור לכספים: חיוב מיוחד

מצב כמו "שיפוץ" יכול לפתוח **טיוטת חיוב מיוחד מהדיירים**. הוא מקושר לקרן ולסכום ה-RFQ הזוכה, ופועל לפי תהליך החיוב המלא שמוגדר ב[מסמך 12](12-payments.md#1241-תהליך-חיוב-מועדים-התראות-וסנקציות): מועד סיום, התראות וסנקציות.

## 18.7 הרשאות ושינויים

- **עריכת הפרופיל**: ועד **וגם** חברת ניהול. אפשר להגדיר שינוי שדורש אישור של הצד השני, למשל חברת הניהול מוסיפה ציוד והוועד מאשר.
- **הצעות שינוי**: מבקר, טכנאי או ספק יכולים להציע ("נמצא גנרטור שלא רשום"), וההצעה ממתינה לאישור.
- **היסטוריה**: כל שינוי נרשם ביומן הביקורת. **ציר זמן של הבניין** מציג שינויים, מצבים, ביקורות ותקלות מרכזיות.
- **מצב בתאריך**: אפשר לראות את פרופיל הבניין כפי שהיה בתאריך מסוים, למשל בזמן ביקורת.

## 18.8 הקמה מהירה

- **תבניות בניין**: מגורים קטן, מגדל מגורים, מגדל משרדים ובניין מעורב.
- **אשף שאלות**: "כמה כניסות? כמה קומות מעל ומתחת לקרקע? יש מעלית? כמה? חניון תת-קרקעי? ספרינקלרים? גנרטור? מקלט?". מהתשובות נוצרים הפרופיל, הדרישות ותכניות התחזוקה.
- **ייבוא מאקסל** לרשימות יחידות וציוד.

## 18.9 מימוש טכני

- **שדות ליבה קשיחים** (טבלאות רגילות) לכל מה שהמערכת מחשבת עליו: קומות, יחידות, שטח, סוג.
- **שדות גמישים** ב-JSONB עם **הגדרת סכמה** לכל סוג (`attribute_schema`). הערכים נבדקים בשרת מול ההגדרה, בלי טבלה חדשה לכל התאמה.
- **קטלוגים דו-שכבתיים**: רשומות פלטפורמה (`tenant_id` ריק) ורשומות לקוח, עם RLS.
- **מנוע כללים** פשוט ודטרמיניסטי: תנאי JSON על הפרופיל ← רשימת השפעות. כל הפעלה מתועדת.
- **עץ** באמצעות `parent_id`, עם נתיב מחושב לשאילתות מהירות.

## 18.10 מודל נתונים

| ישות | שדות עיקריים |
|------|---------------|
| **BuildingNode** | tenant_id, building_id, parent_id, kind (entrance/floor/unit/common_area/element), element_type_id?, name, level (קומה, כולל שלילי), path, attributes (JSONB), active |
| **ElementType** | tenant_id? (ריק = פלטפורמה), key, name (i18n), allowed_parent_kinds, attribute_schema |
| **AssetType** | tenant_id?, key, name (i18n), category (safety/vertical/water/electric/hvac/access/other), attribute_schema, base_type_id? (הרחבה של סוג קיים) |
| **Asset** | tenant_id, building_id, node_id, asset_type_id, responsibility (common/unit_owner/management_contract), attributes (JSONB), install_date, status |
| **CustomFieldDef** | tenant_id, target (building/node_kind/asset_type/unit/person/ticket), key, label, type, options, required |
| **ProfileRule** | tenant_id?, name, condition (JSON), effects (JSON), active, version |
| **RuleApplication** | rule_id, building_id, applied_at, created_items (JSON), approved_by |
| **StateType** | tenant_id?, key, name (i18n), default_effects (JSON), allowed_scopes |
| **BuildingState** | tenant_id, building_id, scope (building/node/asset), scope_id, state_type_id, status (proposed/active/ended), planned_start/end, actual_start/end, effects (JSON), activated_by, linked (rfq_id / charge_plan_id / ticket_id / claim_id) |
| **ProfileChangeRequest** | building_id, proposed_by, change (JSON), status, decided_by |

## 18.12 שלבים

| שלב | יכולות |
|-----|--------|
| **MVP** | עץ בניין (כולל קומות שליליות ואלמנטים), קטלוג פלטפורמה לאלמנטים ולציוד, שדות מותאמים, ציוד בתוך יחידות עם שדה אחריות, כללים נגזרים בסיסיים (אישורים וקטגוריות תקלה), מצבים קבועים עם באנר, הודעה וחיוב מיוחד, אשף הקמה ותבניות, ציר זמן |
| **שלב 2** | סוגי ציוד ומצבים שהלקוח מגדיר, עורך כללים, השפעות מלאות (SLA, חסימת הזמנות, ביטוח), הצעות שינוי ואישור דו-צדדי, תצוגת פרופיל לפי תאריך |
| **שלב 3** | הצעת מצב אוטומטית מחיישנים (למשל הצפה), כללים שמחוברים לבניין חכם |
